# ADR 0009: OpenID Connect (`auth/oidc`)

| | |
|---|---|
| Status | Accepted for what is Claude's to decide; the API it implies waits for epistemer's lock of [interface-oidc.md](../interface-oidc.md) |
| Date | 2026-11-17 |
| Roadmap item | M8.0 |
| Deciders | Claude, as owner. The API choices (interface-oidc.md, "Decisions to lock") are epistemer's |

## Context

`v0.3.0` adds signing in with an identity provider (Google, a company's
IdP) as the second module method, after passkeys. The engine already
drives modules (A21, A22, A24). These questions need answers:

1. which library;
2. the protocol: which flow, and what binds a callback to its flow;
3. what an identity is, and how it is linked to a user, never by email;
4. what happens to an identity linked to no one (sign-up);
5. whether a provider's sign-in is one factor or two;
6. throttling, given there is nothing to guess;
7. where a provider's settings come from, when an app has several.

## Options and decisions

### 1. The library

| Option | For | Against |
|---|---|---|
| **`github.com/coreos/go-oidc/v3` v3.21.0 with `golang.org/x/oauth2`** | The usual Go verifier: discovery, a key set that refreshes itself, ID token checks (signature, `iss`, `aud`, `exp`); the ADR 0004 spike wrote a method on it; six modules | Discovery and key fetches make HTTP calls of its own |
| Our own on a JOSE library | Every check in sight | ID token verification, key rotation and discovery are where OIDC bugs live; ours would be new |

**Decision: go-oidc v3.21.0 and x/oauth2**, in the nested module only;
none of their types in the API. Discovery runs on the first `Challenge`,
not in `New`, so an app starts while its IdP is down; it is cached.

### 2. The protocol

**Authorization code flow with PKCE (S256), `state` and `nonce`**, all
three random, 256 bits, kept in the flow's method state, never in a URL
the app builds. `Challenge` returns the authorization URL; the app
redirects the browser there. The provider redirects back to the app's
callback route, which proves the callback's query on the flow the flow
cookie names (`SameSite=Lax` cookies travel on that top-level GET).

- `state` is compared in constant time with the flow's, so a callback
  can't land in another browser's flow (login CSRF): the attacker would
  need the victim's flow cookie and the state the server made for it.
- The code is exchanged with the PKCE verifier and the client secret,
  over an HTTP client with a timeout; the ID token is checked by go-oidc
  (signature by the provider's keys, `iss`, `aud` as the client ID, `exp`),
  then here: the `nonce`, `azp` when there are several audiences, a
  subject of 1 to 255 bytes, and RFC 9207's `iss` parameter when the
  callback carries one.
- Options expire ten minutes after `Challenge`: a provider's sign-in page
  takes longer than a passkey prompt.
- The provider's access and refresh tokens are discarded: auth signs in,
  it doesn't call the provider's APIs.

Implicit and hybrid flows, and front-channel ID tokens, are not offered.

### 3. Identities and linking

**An identity is its issuer and subject**, the credential's key
(`issuer \0 subject`). It signs in only the user it is linked to, found
through `MethodInput.Find`. It is **never linked by matching an email
address** (§5.5.2): a provider's email can be anyone's, and a verified one
at one provider says nothing about who holds the account here.

Linking happens in an `Enroll` flow, from a verified session with a fresh
second proof (§5.1.9), as any credential's: the engine refuses an identity
someone already holds (rule 10 of §5.5).

### 4. Sign-up

An identity linked to no one arrives as `MethodResult.Unlinked` (§4.9).
The draft first called an app's hook inside `Prove`; review 0024 showed
that the app's user creation would then run inside or beside the
engine's write transaction, and a refusal after it would leave an orphan
user. So **`Prove` returns the flow with the identity it holds, and the
app calls `Link` after its own sign-up step** (an API choice, below). The
engine applies one rule: **a user `Link` names must be new to auth** (no
password, credential, recovery codes, device, session of any age, or
recovery or invitation under way); otherwise nothing is stored. That
stops an app linking an identity to an account it found by email; an app
that names an account it pre-provisioned is beyond what the engine can
see, so the contract says `Link` names a user made for this identity.

### 5. One factor or two

**A provider's sign-in is one factor unless the provider is configured as
two** (`two_factors`, default false). A company's IdP that enforces MFA
can be trusted for both; a consumer provider can't be known to. The `amr`
claim is not trusted: providers fill it inconsistently. An identity is
never an enrolled second factor (§5.5.11): enrolling one doesn't stop a
code to an address counting, and it isn't offered as a second proof.

### 6. Throttling

A callback proves a code the provider issued for this flow's PKCE
verifier: there is nothing to guess. Counting it against the user would
only let a stranger lock a user's provider sign-in from many addresses,
as A22 found for passkeys. **Its attempts count toward the address alone**
(or a trusted device's pair, §5.8.6). The core gains a way for a module
to say so (an API choice, below); `auth/passkey` adopts it, replacing the
core's list naming passkeys.

### 7. Settings

cfgx makes a getter per key, named by its path, so one getter interface
can't serve two providers. The choice (below) is between a getter
interface for one provider, filled by `authschema.OIDC()` for the first
and by a small adapter for others, and a struct of values. The user's
rule favours getters.

### 8. One mailbox, one factor

Review 0024 found that a mail provider's sign-in and a code emailed to
the same mailbox would make two factors from one account. A proof can
now name the address it shows control of (`MethodResult.Address`, an
identity's verified email), and the engine treats it as one that came
through that address (§5.7.2).

### 9. Discovery and the network

Discovery runs lazily in `Start` or `Verify`, coalesced, caching only a
success, so a callback that lands on another instance still verifies.
Its endpoints must be https and the document's issuer the configured
one, against SSRF through a rogue document. One HTTP client, with a
timeout, no redirects and a response cap, serves discovery, the key set
and the exchange. A provider that is down is the method's own failure,
which takes back the attempt's count, not a refusal.

## Consequences

- The module's API is epistemer's to lock; nothing of M8.2 starts before.
- The core gains, if locked as recommended, `Flow.Unlinked` and `Link`,
  `Identities` and `Unlink`, `MethodResult.Address` and the optional
  interface for address-only throttling; `authschema` gains `OIDC()`. The core and authschema are tagged `v0.3.0` with the module.
- An app's callback route is a GET that changes state; it is safe because
  `state` binds it to the flow, and it goes through `Load` like any other.
- §9 keeps out: front-channel and back-channel logout, refresh tokens and
  calling the provider's APIs, the `amr` claim, dynamic client
  registration, SAML, and linking by email in any form.
