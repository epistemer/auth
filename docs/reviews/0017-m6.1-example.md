Ten findings: nine accepted, one declined. The example is what apps copy,
so a pattern that is only unwise there counts as a defect.

| # | Finding | Severity | Triage |
|---|---------|----------|--------|
| 1 | `/api/sign-in` skipped the code challenge when the first call carried a `code`, and finished an unverified session | Critical | **Accepted.** The challenge no longer depends on the request; a code sent with the password is ignored and the code is still asked for. Not a bypass (the session was unverified and refused where it should be), but a trap to copy. Test: a first call with a code answers `next: code` |
| 2 | `/step-up` re-proved the password, so a verified session refreshed its proof for a payout with the password alone | Critical | **Accepted.** The step-up proves the emailed code, as §6.3 proves the second factor; the password only when no code is offered. Test: a payout is refused between `/step-up` and its code |
| 3 | The policy let everyone, staff included, sign in unverified and trust devices, unlike §6.1 | Critical | **Accepted.** Whoever holds `payout.approve` gets `Policy{}`; a store error counts as staff. Test: a staff member without an address isn't signed in |
| 4 | `run` closed the store while requests and the sweeper were still running; the first Sweep came after an hour | Major | **Accepted.** `run` waits for `Shutdown` and the sweeper before `db.Close`, sweeps at start, and stops both when `ListenAndServe` fails. The re-check found the deferred `Wait` running before `cancel`, which would hang on a failed listen; fixed and run by hand both ways |
| 5 | `/api/sign-in` and `/api/refresh` were outside `Load`, so the client's address was empty and the throttle counted every API client as one | Major | **Accepted.** Both go through `Load(Bearer())`. Test: the API session records its client's address |
| 6 | Only the emailed code was offered, so a user with another second factor would finish unverified | Major | **Declined.** The shop enrolls no other factor (it has no enroll route), so after the password `Offers` holds nothing else; a comment marks where an app with authenticator apps offers them. The re-check agreed |
| 7 | Tests that would pass with a rule broken: no `/reports` allowed, Omar's verified sign-in unchecked, a cross-origin sign-in's side effects unchecked | Major | **Accepted.** An unverified analyst reads reports, Sara does, Omar doesn't; Omar ends verified; no code is mailed after a cross-origin sign-in. A step-up from an unverified session can't happen here: a customer with an address always ends verified |
| 8 | `Retry-After` added a second to whole seconds | Minor | **Accepted.** Rounded up, at least 1 |
| 9 | The demo couldn't be signed in to: codes went nowhere, and `Send` logged addresses | Minor | **Accepted.** `Send` logs nothing; `SHOP_DEMO_MAIL` names a directory the demo writes each message to |
| 10 | A comment named the field `code_flow`; one struct served two endpoints | Minor | **Accepted** |

Mutation checks: reverting each of fixes 1, 2, 3 and 5 fails a test.
