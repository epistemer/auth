# Review 0019: M6.3, a security review of the whole package

| | |
|---|---|
| Date | 2026-11-16 |
| Under review | Every source file of `auth` and `auth/access` and the internal packages (the zxcvbn port left out: it estimates, it decides nothing), against interface §5 and the amendments |
| Reviewer | Gemini 4 Argon (High) through agy, the strongest model agy offers for this, about 739k tokens (it read the whole package); the fixes checked by Gemini 4 Argon (Medium), about 112k tokens. A lookup by Gemini 3.8 Flash (Low), about 14k, chose between Argon and Hydrogen |
| Triage | Claude |

Fourteen findings: eleven accepted, three declined. The check of the
fixes raised ten points: six accepted, four that didn't hold.

| # | Finding | Severity | Triage |
|---|---------|----------|--------|
| 1 | A code to an address still counted as a second factor once the user had an app: a step-up adding the password to a session that signed in by code, a sign-in proved before the app was enrolled and finished after, or concurrent first proofs | Critical | **Accepted.** Once a factor is enrolled, only it or a recovery code is a second method in every count of two factors; sign-in's and step-up's `Finish` count again under the write lock; the step-up's device rule too. Tests: both paths, and an app enrolled between the view and the transaction for each |
| 2 | A right password cleared the user's and the pair's counters, so whoever knew it could guess at an app without end from a few addresses | Critical | **Accepted.** Each kind of secret (passwords, address codes, apps and recovery codes) has its own user and pair counters, which only its own success clears; an attempt that tried nothing or found its flow gone takes back its count. Tests: re-proving the password between app guesses, and proving a mailbox code between password guesses, both meet a wait |
| 3 | A factor enrolled while a recovery's new password hashed didn't stop the recovery | Critical | **Accepted.** `finishPassword` checks enrolled factors inside its transaction. Test |
| 4 | An old password being verified while it changed still made a proof | High | **Accepted.** The proof is recorded only if the password's set time is unchanged, checked in the transaction that records it; counters clear only after. Tests: a change mid-hash, also at the same instant |
| 5 | A session copy from before a step-up acted on the upgraded session | High | **Accepted in part.** A `Session` carries the generation it was read at; `StepUp`, `Enroll`, `RemoveFactor`, `Reissue` and the step-up's `Finish` refuse a superseded one, and reloads inside transactions compare too. Declined: refusing a hand-made `Session` and `Reissue` of one from `Sessions()` (the app is trusted with its own store), and binding enroll flows to a generation (a stolen pre-step-up token can't finish one). Test |
| 6 | Parallel recoveries spend `code.hourly` at once and lock a user out of codes for an hour | High | **Declined.** The hourly cap is §5.3.5's trade between a flooded inbox and a lockout; per-flow `code.resend` doesn't change how much can be sent in an hour, only how fast. An app, a recovery code or a device still signs the user in |
| 7 | An address that folds to nothing was offered, sent to and counted as a distinct channel | Medium | **Accepted.** It is no address. Test |
| 8 | `SignOut` with only a bearer token ends that session; a sign-in leaves a bearer session alive | Medium | **Declined.** Ending the session a bearer request carries is what an API client signing out wants, and it needs the header, so no cross-site request can do it; a new session isn't a continued one. `SignOut`'s doc now says what it does |
| 9 | A wait starts at the `throttle.free`-th failure | Medium | **Declined.** It is what §7's "the sixth attempt waits" pins, counting before the check (A6) |
| 10 | A recovery older than the password still took proofs and spent recovery codes | Medium | **Accepted.** Once it holds a proof it is expired; checked in the view and again in the transactions that spend a code. A recovery with no proof yet looks the same as an unknown login's. Tests |
| 11 | A mail scanner following a pending link took over a recovery the user had proved by code | Medium | **Accepted.** A code proof deletes the pending link. Test |
| 12 | `RevokeUser` panicked on an ID with a zero byte | Low | **Accepted.** Test |
| 13 | An access token with `"app": null` was accepted | Low | **Accepted.** Test |
| 14 | `Finish` of an enroll, a recovery or an invitation didn't clear the insecure flow cookie | Low | **Accepted.** Test |

Points the check raised that didn't hold: a nil session in `finishStepUp`
(it returns `ErrNoSession` first; the later `cur` is a device), and a
re-imposed wait in `release` (it restores the counter exactly, or only
shrinks the wait).

Mutation checks: removing each fix fails its test, 20 removals in all. Two fixes
have no test of their own, since only a race reaches them: the refund of
an attempt whose flow went, and the step-up's device rule (an address code
isn't offered once an app is enrolled).

The behaviour changes are recorded as amendment A20, and ADR 0007 points to
it.
