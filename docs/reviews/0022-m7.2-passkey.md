Six findings: three fixed, two fixed in part, one declined. The check of
the fixes confirmed them and raised four points: three fixed, one
declined.

## The review

| # | Finding | Severity | Triage |
|---|---------|----------|--------|
| 1 | With attestation `none` the library never parses the credential's public key, so a registration could store a key that is missing, off its curve, of another kind than its algorithm, or a weak RSA key: a factor that can never sign in, which still brings recovery codes and ends address codes as a second method | High | **Fixed.** `register` parses the key; the library checks an EC2 or OKP key's algorithm, curve and length, and the module adds RSA's: algorithm RS256, at least 2048 bits, an odd exponent from 3 to 2³¹−1. A key with no algorithm is `malformed` |
| 2 | Rules of §5.13 without a test that fails without them, at both levels | High | **Fixed in part.** Added: a registration without UP, with `topOrigin` alone, expired, or with an attested ID other than `rawId`; an assertion with a bad signature by the right key, an origin in capitals or with `:443`, a lost BE flag, a cleared BS flag stored, no user handle accepted when the options named the user's passkeys; the exact IDs and transports of `excludeCredentials`; a self-attestation that verifies is accepted. The engine's own rules (the limit of 20, throttling, the factors' lifecycle, `Within`) are tested in the core with a fake method (review 0021); after the check, one test of each of the first two runs through the real module too |
| 3 | A request for a known user with no passkeys bound no user, so another user's discoverable passkey was left to the engine's rule 3 | Medium | **Fixed.** The options bind the user whenever the engine gives one |
| 4 | Smaller checks: `rawId` against the attested ID; the AT flag on an assertion; the state checked after parsing; `user.id`'s length; a record of another version in `Start`; library parse errors inside `Verify` given the wrong reason | Low | **Fixed in part.** `rawId` must equal the attested ID (`malformed`); the state is checked first; `user.id` is 1 to 64 bytes; `descriptors` checks the version. The AT check was dropped: the library's parse refuses AT without attested data, and the signature covers any that is there. The reason given to a parse error inside the library's `Verify` stays: the response is refused either way |
| 5 | A loose base64 for an Android hash; a last label in hex or octal | Low | **Fixed.** Strict base64url; a last label that reads as a number, in any base, is refused |
| 6 | The generated records and `go.sum` weren't in the diff | Low | **Declined.** They are committed; the diff left them out |

The reviewer found these hold up: the arguments to go-webauthn's two
`Verify` functions (explicit top-origin mode, no cross-origin, DER
signatures, the strictest attestation policy, no metadata provider beyond
trust anchors, no AppID), `New`'s checks, exact origin matching (the
library would fold case and default ports), the RP hash, UP and UV, the
backup flags, the counter, the user handle, the options before the first
proof, and that no library text, challenge, response or credential ID
leaves the module.

## The check of the fixes

| Point | Triage |
|---|---|
| An RSA exponent above 2³¹−1 passes registration and can't verify | **Fixed** |
| `ParseUint` alone lets a decimal last label too long for 64 bits through | **Fixed**: digits alone are refused too |
| No test of a valid non-`none` attestation; none of a BER-encoded signature | **Fixed in part**: a self-attestation that verifies is accepted. BER is refused by the library's default policy; declined |
| One test each through the real module for the limit of 20 and for throttling by address | **Fixed** (`TestTwentyPasskeys`, `TestPasskeyThrottledByAddress`) |

Every fix has a test that fails without it, checked by mutation. In all,
66 mutations of the module were run; those that survived were checks the
library or another check already made, and were removed.
